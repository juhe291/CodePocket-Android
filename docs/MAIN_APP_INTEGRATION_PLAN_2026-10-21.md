## 测试与一个APK的交付规则

1. 已有539通过/1跳过和133通过保留为基线，不从阶段0或技术选型重新开始，也不重复扩展临时草稿/实验文件管理器。优先复用测试、代码及故障证据。
2. 每批先执行改动涉及的测试，补充主 `MainActivity` 中的实际控件与操作链回归；必要时将实验中的适配器测试移动到共享库或主程序合适层。实验用例通过不能替代主程序集成验证。
3. 用例随新组件按行为契约调整，记录原因；不冻结测试总数，不为“全绿”删除失败断言或跳过关键路径。未受影响的结果可保留缓存并注明，只有新改动/失败/未解决问题才扩大或重跑。
4. 交付批次执行完整主程序回归、Lint与 `:app:assembleDebug`，按受影响范围运行Python/打包字节码/Shell/片段检查。核对实际APK的包名、原签名/数据升级路径、ABI、归档、DEX/资源、许可证和运行时依赖；测试类不得打包。
5. GitHub Actions主工作流继续生成可下载的主Debug APK。`editor-lab` 及其手动工作流只作内部验证，不作为第二个产品交付，不要求每个文档或无关改动构建两份APK。
6. 每批报告主程序实际入口、完成与缺失项、测试/缓存/跳过、构建和未验证设备行为。只有I1至I4的主程序链路通过后，才能称“已完整整合”；旧原生主包和实验包保留为整合前基线，当前I1主包是尚待I2/I3验收的集成Debug。
