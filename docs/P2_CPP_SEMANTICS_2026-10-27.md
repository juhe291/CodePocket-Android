## 本批四组修改

1. 固定 clangd 21.1.8 / Termux 21.1.8-3 及九文件原生闭包。准备脚本默认离线、校验摘要；原生代码从安装后的 nativeLibraryDir 执行，头文件从 APK 解压到私有目录。新增独立 `:cpp_analysis` 服务和有代次的 JNI 子进程句柄。超时/销毁只关闭其拥有的子进程。
2. 有界 UTF-8 LSP 通道、UTF-16 坐标、版本与真实签名。支持 `. / -> / ::`、标准库、重载、中间词尾部替换及 `$0` 光标；拒绝越界、额外文件编辑和不支持的片段语法。词法/内置参考回退继续明确标识。
3. 内部目录与 SAF 的新鲜 C++ 源码/头文件快照，加入有效恢复草稿。主文件正文通过 didOpen/didChange 发送，普通输入保持 URI；其他文件代次变化重启分析进程。分析不写原文件、不改变保存冲突基线。
4. 接入既有 Main/Sora 候选和参数窗口，沿用选择、按键、撤销、保存与迟到结果保护。帮助与许可新增单一 C++ 入口，分别查看许可证、NDK 通知、对应源码位置和重新链接说明；不继续调整装饰。

## 发现与修复依据

同一活动 URI 新增 `#include <vector>` 时，clangd 诊断已使用新头文件，补全却仍使用旧预编译上下文。仅等待诊断不足。当前按初始注释/预处理指令前缀变化重新打开主文档，普通正文输入仍用 didChange；真实标准库场景已通过。其他头文件内容代次仍按前置结论重启进程。

clangd 会返回不属于输入前缀的模糊索引候选；本 App 沿用前缀补全行为，关闭 all-scopes-completion 并过滤不匹配前缀。没有把编译器的模糊结果误作静态词法列表。

官方 [clangd 协议扩展](https://clangd.llvm.org/extensions) 说明诊断调度和 `wantDiagnostics`；本驱动显式请求当前版本诊断，测试同时核验实际补全，未把“收到诊断”单独视为语义成功。

## 构建与许可交付

本机复用 `.tools` 中固定输入：

```powershell
& .tools/python313-full/tools/python.exe scripts/prepare_cpp_runtime.py --fetch-host
```

全新环境需显式加 `--fetch`；脚本只下载锁定的公开依赖并核对摘要，Gradle 本身不隐式下载本组件。`scripts/build-local.ps1 -FetchCppRuntime` 提供同样的显式入口。继续使用原 Debug 签名，不更换密钥。

完整 LGPL 库源码、原始构建脚本、动态字符串修补脚本和锁文件随 APK 资产交付。库按独立 `.so` 链接，可替换并重新构建；详细说明见 `app/src/main/assets/cpp-licenses/README.txt`。APK 中的实际原生/头文件/源码/通知检查由 `scripts/verify_cpp_apk.py` 执行。

GitHub Actions 的依赖准备步骤曾被自动审批拒绝。用户在本轮明确授权后，仅补齐既有 `build-apk.yml` 中一条固定依赖准备步骤；原任务、触发条件和发布行为保持。未推送、触发或运行远端 Actions，不能将本地主机结果称为远端 CI 已通过。

实际 APK 检查发现 Android 资产合并会将 `.tar.gz` 解压并去掉 `.gz`，源码正文虽完整保留，资产名和原始归档摘要却与清单不一致。中间包没有交付；改为 `libiconv-1.19-source.tgz` 后重新定向及整批检查，保留原始归档字节。原始失败日志与变换证据保留，最终结果以实际 APK 检查为准。

新配置 App 级 NDK 后，Gradle 还会重新剥离旧 `libchaquopy_java.so` 和 `libtermux.so` 的调试信息。实际比较证明合并前输入与历史包字节一致；本批明确保留全部共享库原始字节，重新构建后再次逐项比较。不能仅凭源文件未改就宣称原运行制品保持。
