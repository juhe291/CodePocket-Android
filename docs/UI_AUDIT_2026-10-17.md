原生 Kotlin + Android View，没有 Compose、Sora、Tree-sitter、LSP 或真实终端渲染器。Gradle 8.9（Wrapper 含 SHA256 校验）、AGP 8.7.3、Kotlin 1.9.25、JDK 17；Chaquopy 17.1.0、Python 3.13；compileSdk/Build Tools 35、targetSdk 34、minSdk 24，仅 arm64-v8a。正式源为 Google/Maven Central。本地便携工具在忽略提交的 `.tools/`。

[Chaquopy 官方兼容表](https://chaquo.com/chaquopy/doc/current/versions.html) 列明 17.1 支持当前 AGP/Python/minSdk 组合，本轮实际强制构建也通过。targetSdk 34、旧窗口 API、单 ABI 和缺少完整发布通知仍是后续事项；不为这次 UI 审查盲目升级构建链。

`MainActivity.kt` 当前 1812 行；`CodeEditor.kt` 12 行，只继承 EditText 并转发选区变化。文件/执行/部分编辑规则已分模块，但界面、焦点、输入、菜单和状态仍集中在 Activity；大量代码直接依赖 Editable、TextView.Layout、选区和原生 Span，替换编辑器绝非修改一个类名。

## 5. 编辑器架构是否够用，是否替换

**判断：短期足以安全重做外层 UI；中长期不宜继续在 EditText 上堆叠复杂绘制、光标动画和解析。推荐先建立适配接口并做 Sora 隔离原型，再决定默认编辑器切换。**

现架构可以呈现 LSP 返回内容，因为已有文档/版本和后台请求保护；但尚没有 URI 映射、语言服务生命周期、协议增量文本、诊断、项目配置、跨文件索引或取消/重启。词法候选与参数资料不能承担这些职责。EditText 并非不能接语义后端，问题在于目前没有相应服务层及编辑器契约。

## 6. 真实运行和本地 C++ 的判断

Python 是真实离线引擎；当前流程为预设 stdin → 独立 :python 进程 → 最终 JSON 结果，6 秒字节码监控、父会话 10 秒含初始化，native 阻塞由父进程终止。运行进程仍与 App 共用 UID，不是安全沙箱。标准输出截断上限 50000 字符，代码 100000、stdin 20000；多文件 import 和外部资源在主机已有回归，完整设备进程行为仍待验收。

C++ 使用真实 Wandbox，先查询编译器，再发当前单文件 code/stdin 和 `-std=c++17`；没有 API Key。本轮在线脚本 `gcc-13.2.0` STL/stdin 真正得到 `8\n`、退出码 0；第二个编译错误用例在 TLS 握手出现 `UNEXPECTED_EOF_WHILE_READING`，第三个退出码 7 用例未执行。脚本退出 1，**在线回归仅部分通过**，不能称服务全面稳定；这不是 Android APK 启动结果。没有为了测试关闭 TLS 校验或修改网络配置。当前没有分阶段计时，不能把速度问题全部归因于 App 或编译器。

不以“NDK 有 clang”推断普通 APK 可在手机编译运行。[Android 官方文档](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission) 对目标 API29+ 应用私有可写目录执行有明确限制；本地方案须分开验证编译器本体、头文件/STL、生成物如何执行、架构与加载策略、体积/许可和进程中止。主机 g++ 模板通过只证明模板有效。短期继续保留云端后备。

真实终端需要渲染器与可持续 I/O 会话共同实现。[xterm.js](https://xtermjs.org/) 是终端前端，[许可](https://github.com/xtermjs/xterm.js/blob/master/LICENSE) 为 MIT；接一个 WebView 或 ANSI 配色不会使现有 StringIO/单次 HTTP 协议变成可交互终端。后续应先给 Python 建立输入队列/流式输出/等待输入/停止契约，再评估 Android WebView 或原生渲染器；云端批处理模式保持如实说明，不提供系统 Shell。
