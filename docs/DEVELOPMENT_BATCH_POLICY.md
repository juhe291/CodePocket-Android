# 开发批次与验证节奏

2026-10-26按用户补充更新：可以先积累几项相关修改，再统一构建App。本节奏适用于后续工作，旧阶段结果保留其历史含义。

## 批次边界

- 通常将3–5项相关UI/交互修改作为一批；围绕同一页面、共享组件或完整使用流程组织，不机械按文件数量拆分。
- 批次开始先列出范围、手机/平板影响及需要保护的现有行为。继续UI视觉优先、未实现新功能暂缓、实机统一后置的约定。
- 单项完成后做受影响的定向测试和必要视觉检查；需要定位编译问题时运行相应编译任务。不要默认每个小修改都跑全量或生成APK。
- 出现启动崩溃、输入阻断、文件安全或真实运行入口回归时及时处理，不为凑批次延后阻塞问题。新发现的其他问题按现有约定记录，不擅自扩大本批范围。

## 批次收尾

1. 检查本批整体手机/平板布局、深浅主题和相关菜单/焦点/状态；记录实际看过的图和自动断言的范围。
2. 统一执行主App全量回归、相关模块Lint、Debug APK构建；失败时分析并修复，保留日志，不删断言或跳过失败来获得通过。
3. 检查APK元数据、签名、完整性和对齐。运行入口、运行模块、相关依赖或运行相关打包内容有变化时执行相关Python/终端/片段专项；这些路径未变时可引用上一批有效验证，但须注明复用及内容哈希依据，不冒称本批重新执行。
4. 成功后交付一个本批最终APK、集中修改说明、测试结果及已知问题。一般不为每个小改动单独复制一份dist安装包；已交付的历史产物保留。
5. 收尾检查已通过且没有新的变更/失败/未解决疑点时，不重复跑同一套完整检查。

纯文档、计划或说明调整只做内容、链接和差异检查，不因此构建APK。当前最新已验证安装包继续沿用[选择器合并批次APK](../dist/CodePocket-pickers-batch-2026-10-26-debug.apk)；完成下一开发批次后再更新。
